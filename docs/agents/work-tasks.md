# Work: tasks

A linked Work workspace's Tasks view, and Done as the owner accepting a thread's work (milestone 25).

## The view

`src/renderer/src/work/tasks/TasksView.tsx`, registered by `tasks/view.ts` as a lazy chunk. It reads the sector's open tasks through work-kit's shared task client (`createLifeosViewsClients` in `work-kit/lifeos`, made in `tasks/client.ts`) on the workspace's LifeOS session, which is narrowed to its sector. The groups are LifeOS's own (`groupTasks` from `work-kit/lifeos/tasks`): the first of Today leads with Start thread, Done and Snooze; then Today, This week, Later and Waiting. A row's due time gives way to Start on hover; its menu leads with Start thread. Open shows the task in full in a sheet (`TaskSheet.tsx`, `tasks:get`); New task in the header makes one (`NewTaskDialog.tsx`, `tasks:create`). The column's Tasks row shows the open count (`useOpenCount`, tasks/facts.ts).

Start thread is `startThread(chip)` with `{kind: 'task', label, ref: {at: 'lifeos', table: 'tasks', id}}`: a new thread's composer with the chip in it, and nothing runs until he sends. The first send carries `about`, and the host links the thread to the task (`ctx.links.link`).

## Open a code thread…

A task's menu (a row's and the lead's right-click) and the task sheet's foot offer Open a code thread…, which starts a thread on the task in a code workspace (`tasks/CodeThreadDialog.tsx`, the pure parts in `tasks/codeThread.ts`). The dialog lists the rail's code rows in the rail's order, pinned first, a workspace linked across hosts once, as its first copy on a host with Work on (the lead's when its host has it): a host with Work off refuses a create that carries `about`, so a row with no such copy is left out. A search field above the list narrows it by name; ↑↓ in the field move the pick, and a host's name shows only where two rows share a name. Project shows once the picked workspace has projects (that copy's own, archived ones left out), None by default; a pick the search moves to another workspace drops the project (`pickedProject`). Start calls the view's `startThread(chip, {cwd, projectId})`: `workStartPort` moves the window to that workspace and opens a draft there by project (none for None, never the folder's local project), with the chip in its composer. The chip leads the draft and replaces a LifeOS chip an unsent draft there still held from an earlier start (`startAboutChip`, Start thread's too), so the first send says the thread is about the task just picked. For a workspace that cannot read LifeOS, Start pressed before the task's notes load spins until they do. Nothing runs until he sends; the first send carries `about`, and the host links the thread to the task as Start thread's is linked.

What the thread may read of the task follows the workspace's own LifeOS link, never widened for this: a code workspace linked to the Work workspace's sector (`work.lifeos.link`) reads LifeOS through its own sector key, so its chip is the task's plain chip; any other gets the task's title and notes as text in the chip (`quote`, which `chipLine` writes under the chip's line), and no LifeOS reach. Both chips name the task, so the link is made either way.

The Tasks view names only the pure work-kit modules (`work-kit/lifeos`, `work-kit/lifeos/tasks`, `work-kit/views/lib/*`); the client types come off the maker in `tasks/client.ts`. Naming `work-kit/views` in renderer source, a comment included, brings its Kobra components into `work-kit-sources.css`; the Agenda does, for its Week and Month.

## `work.tasks.done {taskId}` (approve)

Done in the view goes through the host, not straight to LifeOS. `tasks/index.ts` reads the task's links (`workLinks:byEntity`) and its sector (`tasks:get`), and completes it with `tasks:complete {id, reason: 'Accepted the work of "<thread title>"', threadLink}` naming this host's newest linked thread of the task's own sector: a Work thread of that sector, or a code thread opened on the task whose workspace is linked to that sector or to none (`worksIn`); with none, it completes it plainly. A code thread on another host than the Work workspace's is not named. Answers `{threadId, nextId}`. A send that goes still completes the thread's linked tasks through `ctx.links.completeFor` (the hold's own path).
