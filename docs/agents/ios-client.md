# The iOS client: ios/TempCodeClient and ios/TempCode

- docs/IOS-DESIGN.md fixes the phone's design: information architecture
  (Home in two levels shaped like the desktop's sidebar, a project as its shell in the detail; Inbox; Search), the thread
  screen per type (board, plan, fleet, sources as the hero with the chat as
  a second segment), tokens, exact motion values and the performance rules.
  iOS threads build to it and do not re-decide what it states.
- The phone's numbers are written once: the transcript's type and lengths
  are the client package's `TranscriptScale` and `TranscriptLengths`
  (Design/TranscriptScale.swift; the desktop's ladder on iOS text styles,
  prose 15/22, lines 13/20, details 12/16), drawn through Tokens.swift's
  `.transcriptType(_:)`, `TranscriptType` and `TranscriptMetrics`; the
  Live Activity target links `TempCodeClient` too, since it compiles the
  shared Tokens.swift. The desktop in-out curve is asymmetric; its Swift
  test checks its Bézier midpoint rather than assuming symmetry. The
  motion numbers are `MotionValues` (Design/MotionValues.swift, the
  desktop's durations, curves, springs, holds and loops exactly), which
  Design/Motion.swift turns into animations. Two vitest guards run on the
  box: scripts/ios-motion-parity.test.ts fails when a `MotionValues` line
  differs from index.css, lib/ease.ts or the holds, and
  scripts/ios-literal-guard.test.ts counts every literal duration, curve,
  font size or row height under ios/TempCode/Sources/{Thread,Shell,Design}
  outside Tokens.swift and Motion.swift against a per-file allow-list that
  only shrinks (`IOS_LITERAL_GUARD_PRINT=1` prints the tally).
- `ios/TempCodeClient` (Swift 6 package on the contract package) is the
  phone's connection runtime: `TempCodeSocket` mirrors the desktop supervisor
  (ticket, hello checked against the paired id and contract, jittered backoff
  to 5 min reset after 30 s up, probes on foreground/online/retry, a 10 s
  background grace), `Subscriptions` resumes with `afterSeq` and honours
  `reset`, `SessionCache` is the sqlite3 mirror a cold launch paints from,
  `EnvironmentClient` is what SwiftUI observes; it reconciles its session
  list with `session.changes` from the cursor the cache kept and lists
  whole on `reset`, with no cursor or on an older host (the return flow:
  docs/IOS-DESIGN.md "Background"). A thread's transcript always opens and
  returns at its bottom: no scroll memory, a snap with no motion when the app
  goes to the background, and a cold launch's restored thread at the bottom
  too (`TranscriptLanding` in the client package, `LaunchRestore` in
  Shell/Navigation.swift); only a route that names a row (a search hit, a
  notification) lands on it. Its README has the state
  table and the L3/L4 extension points. `ios/TempCode` is the read-only
  SwiftUI app, generated by `xcodegen` from `project.yml`. Home is the
  desktop's sidebar in two pushed levels (docs/IOS-DESIGN.md "Information
  architecture"): Home lists the workspaces (linked copies as one row) with
  the rail's one status mark (paused, needs you, working with the running
  thread's title, unread) and a Chats row; `Route.workspace(key:)`
  (Shell/WorkspaceScreen.swift) is the middle sidebar: each project as the
  desktop's project card (Shell/ProjectCardView.swift on the package's
  `ProjectCards.card`, Shell/ProjectCard.swift, a port of sidebarRows.ts
  `cardLines`/`masterBlock`/`cardCounts` and projectCardModel.ts: the name,
  the branch line and the mode, then needs you and failed roots as lines
  (never counted), master blocks with `lead`, working and watching, paused,
  unread (never the thread on screen, `EnvironmentClient.visibleThread`, nor
  a housed one), a page of 32 then "N more", and "N dormant", "N archived"
  or "No threads"; a pin earns no line; on the group fill, `Surface.group`
  and `CardMetrics` in Tokens.swift; a needs-you or failed detail drawn as
  plain words, `InlineMarkdown.plain`; a line opens its thread in its shell,
  elsewhere the shell on its landing, a long press or the ellipsis the
  project's menu), then the stray chats 16 pt under the cards.
  `Route.project(key:thread:seq:)` (Shell/ProjectShell.swift) is a project's
  place in the DETAIL column, the desktop's project home: the strip, then
  the thread its chip selects (`ThreadScreen`) or the project's draft (an
  empty body and Shell/DraftComposer.swift: the A10 box as `ComposerBox`,
  the A11 row with the draft's own mode, and the draft row with the type,
  "Name this thread" (80 characters, `ProjectDraft.title`, sent as
  `session.create { title }`), Master for a chat (operate) and the host of a
  linked project with New copy through `project.ensureLinked`; the client's
  `ProjectDraftStore`, one draft per link key or `loose:<workspace>`, 64
  keys for 30 days in UserDefaults `project.drafts.v1` written after 500 ms
  of quiet (`flush` when the draft leaves the screen or the app the
  foreground), photos in memory; the first send waits for the host's
  catalog (`DraftSend.canSend`; a host switch reloads it, `CatalogLoad`) and
  is `session.create { firstMessage }`, or create, upload, send and
  `session.archive` on a failed send, `sendDraft`, carrying the model and
  effort the picker shows (the draft's saved pick only seeds it); the
  catalog load keys on the host and its link (`CatalogLoad.Trigger`), so a
  draft opened while its host was down asks again when it comes up, its row
  reading "Waiting for <host>" meanwhile, and an ask the host answers with
  an error is asked once more after 2 s, then reads "Couldn't load models"
  with Retry, on the draft and the thread composer alike (`CatalogLoad.failed`;
  the seam `TEMP_CODE_FAIL_ANSWERS=method:count` on an isolated instance,
  src/main/server/answerSeams.ts); while it runs the button
  spins and the strip draws its chip (`DraftSending`, live until the meta
  lands); the box empties at the click (`ProjectDraftStore.take`: what was
  sent rides the chip, what is typed meanwhile is the next draft) and only a
  failed create gives the sent text, name and photos back (`restore`); it
  opens the thread in the shell; every New thread focuses the draft,
  `NewThreadPresenter.compose`); `key` is the strip scope's
  key (a project's `ProjectPairs.key`, `loose:…` for a workspace's loose
  chats), `thread` the chip id `<env>:<sid>`. `ShellPaths.place` puts every
  root of a project or of a workspace's loose chats in its shell, a
  subagent pushed over its root's, a chat outside every workspace bare;
  `ShellPaths.land` (a card's tap, `ShellNavigator.openProject`) picks
  `ProjectLanding`'s active thread, else the last one on screen there
  (`ShellLandingStore`, `shell.landing.v1`, per scope key), else the draft,
  and moves nothing while that shell is open; `ShellPaths.identity` keeps
  the shell one screen across its threads. The rules are the package's `HomeSections` (`home`, `workspace`,
  `project`, `RailStatus`, `isActive`; ThreadGroups.swift
  `masters`/`batchHome`), pure over `HomeHostInput` values (ProjectCardTests
  holds the card); the app's `HomeRows` adapts the clients,
  Shell/ShellRows.swift holds the shared rows and `NewThreadPresenter` (New
  thread focuses the project's draft; the new-thread sheet, kept for a
  prefilled brief, presents from the root), and `HomeSlots`
  (Shell/HomeSlots.swift) is where sibling features plug in (host notes,
  host and project menus, project settings, the plan chip and the menu's
  Project Plan row, the host's trailing mark). On the iPhone Duo (plan 1) Home and Search are each one
  `NavigationSplitView` on a `ShellNavigator` (Shell/ShellSplit.swift,
  ShellNavigator.swift: the sidebar's routes, the detail's root and stack,
  `open(route)` placing a route by `ShellPaths.column(of:)` and a thread in
  its shell by `ShellPaths.place`; a notification tap opens Home's shell, a
  search hit the same shell in Search's detail; a thread opened bare before

  later push names it or the host's workspaces or projects push lands (a

  `completeLists`, `catalogStamp` and `watchPlacing`, never its sessions;
  `ShellPaths.relisted`, `awaitsListing`), the pose is the
  client package's `ShellPose` published as `\.shellPose` (read it, never

  (Shell/ThreadStrip.swift over the package's `ThreadStrip` and
  `StripChip.look`, `StripMetrics` in Tokens.swift) sits at the project
  shell's top in every pose (a 40 pt live row, the status mark in the chip's

  compact width the Recent menu with Archived Threads at its foot), and the place is remembered under
  `navigation.memory.v3` (`NavigationSnapshot`; a v2 snapshot gives back its

## The data path's two contracts (the performance pass, 2026-11)

What a push and a key may re-run is written down in docs/IOS-DESIGN.md
"Performance" ("What a push and a key may re-run"), and the client
package's tests hold it: `ObservationIsolationTests`, `PushIngressTests`,
`TranscriptModelTests`, `ComposerDraftTests`. Before changing the client's
state, a list reader or the composer, read that section. The rules a change
most easily breaks:

- **A thread is a `ThreadModel`, never a value in an observed dictionary.**
  Inside the package a thread is written in place through
  `EnvironmentClient.write(_:_:)` and read with nothing tracked through
  `peek(_:)`. A view takes `client.thread(id)` and then the one projection
  it draws (`content`, `dock`, `flags`, `overlays`, `frame`).
  `client.threads[id]` and `ThreadModel.state` answer the whole value and
  run their reader at every write to the thread: only a view that is the
  thread's own page reads them (a board, the fleet, the sources), and only
  while it is in view (`HeroGate`). `ThreadScreen.body` reads `frame` and
  `flags`; a fact it needs is added to `FrameFacts`, kept without walking
  the thread. A view that draws rows never holds a `ThreadState`.
- **Sessions: pick the reader.** `client.session(id)` tracks that session
  alone. `listedSessions` is the list screens' copy, up to 250 ms old while
  no list shows. `currentSession(_:)` and `currentSessions` are the store as
  it is now with nothing tracked: code that acts (a send, the badge, a
  launch route, `markSeen`) reads these, never the trailing list. There is
  no `sessions` property, so a new reader has to choose.
- **A new write to `ThreadFold.items` goes through `set(_:_:)`** (a key
  through `rekeyEcho`, growth through `append`), which records it in
  `FoldChanges`. A write that skips it leaves a stale row on screen;
  scripts/ios-fold-writes.test.ts holds the source to one site of each.
- **A new push kind joins `PushIngress`**, or empties it first, or is
  listed as free of order in `EnvironmentClient.apply`. One that bypasses
  the queue can overtake queued rows.
- **Cache writes go through `CacheWriter`** in the order the client applied
  them; a read that must see them awaits `cacheWrites.drained()`.
- **Nothing below `ThreadScreen` in the dock holds a `SessionMeta`.** The
  dock draws a `ComposerChrome`; an action reads `client.currentSession`
  when it runs. A field the dock needs is added to the chrome.
- **Only the field reads `ComposerDraft.text`.** Everything else reads
  `hasContent`.
- **No `TimelineView`, no `KeyframeAnimator`.** Either one, while it is
  on screen, runs SwiftUI's display link on the main thread every frame. A
  clock is a `Tick` (Design/LiveText.swift); a loop is a Core Animation
  layer (`Motion.repeating`, Thread/WorkingLine.swift); a short fade steps
  its own clock from a task that ends (Thread/StreamFade.swift).
- **A view's body counts itself** where the perf set gates it
  (`let _ = PerfCounters.bump(...)`); a new view on the push or key path
  that should stay still gets a counter and a gate.

The rules every press below keeps (fix round 2):

- **Frozen, then checked twice.** A press freezes its host, the key it goes
  out under (`PressGates.key`: the key's id and words, and the foreground it
  was pressed in, `|f<n>`, which leaving the screen moves on) and what it
  sends before the owner's check. When the system answers, `PressGates.allow`
  looks the host's client up again: another host, or another key on it
  (even one with the same capability), voids the pass and sends nothing
  (`PressGate.holds`). Each wait checks the key once more when its seconds
  end (`SendWait.Check.key`, `SendWait.why`): a key that differs only in its
  foreground is "TempCode left the screen", so a group's next host, or the
  send after a grant, never goes after a background and return. Share waits until the host
  that serves the item's links answered before it offers Create.
- **The ledger's answer is the host's.** `PressLedger.reached` counts the
  host's words and a refusal the phone made before anything left (an
  encode failure is `ActionError`, never `TransportError.decoding`). The
  box's `linkDown` for a relayed Mac (every hand-off the box could not
  finish says `linkDown:`, relay.ts `forward`: a 30-second deadline, its
  service closing, no presence row), a host's `outcome unknown:` (Mail's
  send whose LifeOS answer was lost, mail/index.ts `OUTCOME_UNKNOWN`), a
  lost socket and a yes the phone cannot read (`.decoding`) are not
  answers: the press stays Checking, keeps its attempt key, and is read
  back. The host's "It may have gone" is `.mayHaveGone`, late or not.
- **A late answer reaches its screen.** An answer after the fifteen
  seconds, and every read-back, goes to its kind's hearer
  (`PressLedger.listen`: a reply's desk by its attempt key, a Create
  link's sheet by its item, a request's sheet by its id); a late refusal
  says the host's words on the item, and a press on many says each item's
  own outcome (`runMany`'s `outcome`, `DecisionResult.states`). A pushed
  item settles a lost press on it at once (`PressLedger.heard`, a mail Send
  of a thread's draft too), and a press settled twice is heard once.
- **Each part that has not left is asked again.** A press on many goes host
  by host, and a send waits for its grant's answer: before each part's
  request (the grant's too) the app must be in front, the host linked and
  its key the one he pressed under (`SendWait.mayStart`,
  `HeldPress.dispatch(ready:)`; grouped Discard freezes its keys as Send
  does); a part that may not start is said beside those that went, never
  sent. The record asks the same once more where the request leaves
  (`PressLedger.mayLeave`, set at the root, with the key each press carries
  and the method the key must still press), and the socket asks it again as
  its send queue releases the frame, after any write the frame waited
  behind (`Transport.release`, a task-local the record sets; a grant and a
  link's role go through `PressLedger.guarded`): a press it stops never left,
  its record goes and its site puts the thing back with the line. Every
  press carries the key the owner's check passed (Mail Send, Try Again,
  Create, Replace, Discard, Edit, a clash's answer, a form's Reopen and Undo
  of a Result too; Reopen and Undo, outside the record, through `guarded`). A grant whose answer was lost says
  so (`HeldPress.GrantLost`); a send that did not start after a grant was
  made says the grant stands.
- **One reading of each item's answer.** A group's on-time answer and its
  late one read an item the host could not confirm (`outcomeUnknown`) as
  "May have gone", never "not sent" (`DecisionResult.state`,
  `GroupOutcome`), and so does a request's row, its head and the note to its
  thread (the host keeps `unknown` on the row's result), and the item's own
  page ("May have gone. … Check Sent first.", never "Not sent"). A request
  answered `running` is Checking on the press's own answer too
  (`PressLedger.NotYetKnown`); its end, from a push or a fresh read, settles
  the press even while its first request is still parked
  (`WorkHost.requestEnded`, `settle(final:)`), and a running answer after an
  end changes nothing. A refused key closes the request sheet and drops a
  read or a receipt started under it (`keyEpoch`). Mail's Send, Send Now and
  a hold send it could not confirm, and Messages' Try Again, answer
  `outcome unknown:` when LifeOS may have taken them (server/work/outcome.ts).
  A lost Try Again settles from the conversation's own read, asked once it
  went Checking and awaited (`retryNow`, then the seed: LifeKit drops an
  equal value, so a change is never waited for), by its outbox id, a reply
  the page no longer holds reading May have gone (`RetryReadBack.truths`);
  a reply lost across a relaunch says so on its conversation
  (`MessagesDesks.readBack(…, host:, ref:)`). An attempt key carries when it
  was made (`PendingPress.newAttempt`, `phone-<ms>-<uuid>`): one older than

  (server/work/attemptAge.ts), never "never heard" or sent anew.
- **Undo is on screen for the whole wait.** An item's own page wears the
  Outbox's capsule when the Duo's sidebar is hidden or shows another place
  than the Outbox (`SendUndoPlace`); a thread's held line says a cancelled
  Send itself (`OutboxPresses.notice(for:)`); from
  anywhere else the Outbox's list comes up for a press counting, queued or
  on its way. If he then leaves for another tab or page while it counts, the
  tab he is on shows the same capsule at its root (`outboxUndoFallback`, on
  Home's, Work's, Search's and the Inbox's), drawn only while neither the
  list nor an item's page shows it (`OutboxPresses.surfaces`; the compact
  Inbox carries it outside its stack, so a pushed item or diff shows it); a
  group's refusal is said there too. A press on many's result is kept until a
  capsule in front, with no countdown over it, has shown it for a toast's
  time; a countdown hides it without spending it, and a later result waits
  behind it (`OutboxNotices`). Each cancel of the wait (the app left, a link
  or key lost, a host not paired) is taken into the same queue at once with
  its own id and the items it names, so two links lost together leave two
  lines, said in turn, and a thread's held line reads its item's own
  (`OutboxPresses.collect`) while the capsule is not saying that same line.
  A new press of an item drops its unseen lines (`OutboxNotices.forget`), so
  a cancel's "Not sent" never shows after the Send that followed it. A Mail
  or Messages countdown whose own page is off screen (Back, another tab), and
  a request's whose sheet he closed, has its Undo at the tab's foot too, one
  capsule per countdown, each Undo bound to its own press and true only if
  that press still waited (`ElsewhereUndo.all`, `SendWait.countingOffScreen`,
  `RequestPressWait.offScreen`; Mail's page, a person's page and a request
  sheet count themselves, as a conversation does); a request sheet that covers
  the tab draws the same capsules over itself (`outboxUndoOverSheet`), so Send
  on one request, Close, then opening another never hides the first's Undo.
  A request's outcome that
  lands with its sheet closed is the toast (`RequestPressWait.toldOff`). VoiceOver hears each line once as its clock
  starts, a sum, a refusal or a cancel, as it hears the countdown
  (`OutboxPresses.speak`). A host whose answer was lost counts as "N
  checking" in the sum. At accessibility sizes the capsule's line wraps and
  Undo sits under it.
- **A locked launch keeps the file.** `work-presses.json` holds ids, refs
  and times, under protection until the first unlock. A file that is there
  and will not read is never taken for none: no press leaves and nothing is
  written over it until it reads (`PendingPresses.read`,
  `PressLedger.readIfUnread`, `unreadLine`).

## The Work perf proof

`TC_PROOF_SET=work-perf bun scripts/ios-sim-proof-local.ts` is the Work
performance proof (docs/IOS-DESIGN.md "The Work perf proof"): the perf set's
Measure build, headless, its own runs (`TC_WORK_PERF_RUNS`, default
`launch-today rest-today list-idle list-busy editor`), each launch run by the app itself (`TC_TEST_WORK_PERF`,
`TC_TEST_WORK_PERF_SPLIT`, `Sources/Perf/LaunchFrames.swift`) and added as a
split to `Documents/work-perf/<run>.json`. scripts/lib/ios_work_perf_check.py
judges it against scripts/lib/ios_work_perf_gates.json
(scripts/ios-work-perf-check.test.ts feeds it canned reports). The client
package holds the pure parts under `Support/`: `Signposts` (subsystem
`dev.landon.tempcode`, categories `launch`, `list`, `file`, `press`),
`LaunchMarks` and `LaunchClock` (this launch's marks from the kernel's process
start), `SocketRequests` (the socket's requests, counted in DEBUG and Measure
builds only), `LaunchRowLedger`, `WorkPerfReport` and `WorkPerfWait` (what a
measured launch waits for: every host that can list, a relayed one only while
its carrier says it answers, and Today's fresh page on a launch onto Today; its
note names what never came). In a work-perf run the layout probe stands down,
as in a perf run. It is a hand run (docs/release-gate.md).

The list runs and Settings → Diagnostics' Run List Check share
`WorkListCheck` (Sources/Perf/WorkListCheck.swift): the client package holds
its fixture rows (`WorkListRow.fixture`), the row ledger
(`ListCheckLedger`), the report (`WorkListReport`, the `list` field of a
`WorkPerfReport`) and the checker's words (`WorkListCheckRules`); the app's
own scrolls are `PerfCounters.offsetWrites`, counted where `PlaceTop`
brings a list back to its kept row. Every run also carries the app's
footprint (`WorkPerfMemory`); the editor run's document is seeded by
scripts/lib/ios-work-perf-seeds.ts and its WebKit processes sampled by the
script (`work_perf_webkit`). The guards beside it: scripts/ios-body-reads.test.ts
(a Work view's body and view helpers reach a model only through `PURE_READS`,
each checked in its source, bookkeeping `@ObservationIgnored`),
scripts/ios-tick-ledger.test.ts (every unbounded loop in a Work view is a
clock IOS-DESIGN "Clocks" names, registered in `TickLedger`, which records in
every build), scripts/ios-work-access.test.ts (Reduce Motion, Reduce
Transparency, Increase Contrast and the keys), and the literal guard, which
counts Work's views too.

No socket starts before the first frame, in every build: `AppModel` holds
`LaunchClock.sockets` (a `FirstFrameGate`) at launch, `EnvironmentClient.start`
paints from the cache and then starts its socket only once the gate opens, and
the gate opens at the first frame's mark (or after `FirstFrameGate.cap`, three
seconds, when no frame comes, as in a background launch). The caller is not
held: `registry.sync()` and `ready` come as before.
