# Templates per job

A new document, sheet or deck starts from one of his own. Each Work workspace has a shelf: his templates for that job, our starters for that job, and a group that follows him across jobs. Pillar `templates` (plan `.temp-code/plan-jcTUPnk4t-9Y.md`, round 3's row 5; landing note `.temp-code/plans/landed/R3-templates.md`).

Its folders: `src/main/server/work/templates/`, `src/renderer/src/work/templates/`, `src/shared/work/templates.ts`, `src/shared/contract-work-templates.ts`, `resources/work-templates/`, `scripts/build-work-templates.ts`. Another pillar may import two files: `templates/api.ts` on the host and the renderer's `templates/open.ts`.

## What a template is

A template is an ordinary file of a kind. Editing one is opening its file, and it gains every editor feature as that lands.

| Group on the shelf | Where the files are | Who may change them |
|---|---|---|
| The job's own | `<workspace folder>/Templates/`, top level only | him, in the shelf or in Files |
| All jobs | `<userData>/work-templates/shared/` on the workspace's host | him, in the shelf |
| Starters | `resources/work-templates/<sector>/` and `/any/`, shipped read-only | nobody; Hide per workspace, "Edit a copy" makes his own |

- Forms: `docx`, `xlsx`, `pptx`, `tcdoc`, `tcsheet` (`TEMPLATE_FORMS`, `templateFormOf`). The kind is the form's: document, sheet or deck.
- The name is the file's name without its extension. The id is `job:<file name>`, `all:<file name>` or `starter:<sector>/<slug>`; a starter's slug is `starterSlug(name)`, so its file is `<sector>/<Name>.<ext>` and its key `<sector>/<slug>` (`unify/invoice`, `any/meeting-notes`).
- A workspace's sector (`workspaces.sector`) picks its starters. A workspace with no sector gets `any` alone.
- The groups for all jobs do not sync between hosts: each host keeps its own.
- A dot file, Office's lock file (`~$…`), a folder and a file of any other kind are not templates.

## The shelf (`shelf.ts`, `store.ts`)

`shelfOf(ctx, workspaceId)` reads the three folders at every ask, one `stat` a file. There is no watcher. `work_templates_index (path, size, mtime, fields)` keeps each file's fields, so a file is opened only when its size or time changed; a row whose file left its folder is dropped at the next read. One more is opened at a read: a `.tcdoc` beside a Word file of its name whose pairing is not known yet (below), until it is. `work_templates_hidden (workspace_id, starter)` keeps the starters he hid in a workspace; `workspaceRemoved` drops them.

The shelf's order: the job's own by name, the job's starters, all jobs' own, then the starters for every job. The window draws two groups from it: the workspace's name (his own and the sector's starters) and "All jobs" (`where: 'all'` and `starter:any/…`).

`startersRoot()` is `resources/work-templates` under `appRoot()`: the checkout in a dev tree, the build's folder on the box, the app's own folder in a packed app (the app is packed with `asar: false`, so the files are plain files there). `TEMP_CODE_WORK_TEMPLATES` names another folder; a test uses `setStartersRoot`.

`resolveTemplate(ctx, workspaceId, ref)` takes an id, a starter's key, or a name. By name it looks in the job's own, then all jobs', then the job's starters, then every job's; names match without case. So a template he saved as "Meeting notes" takes ours' place for every caller. A starter he hid is still found by a caller that names it. One of his own with a starter's name (in the job's folder or for all jobs) takes that starter's place on the shelf too, so "Edit a copy" leaves one tile; the starter is still found by its id or key, and comes back when his is renamed or removed. A starter of another sector is found by its id or key (Money in a job with no sector asks for `unify/invoice`).

**What the shelf reads.** A file of the job's `Templates` folder is listed only when it lies, by its real path, where Files' door lets the workspace reach (`locate` in files/policy.ts, asked as his window): the workspace's own folder or a library of this host. A link to a file elsewhere on the disk, or a `Templates` folder that is itself a link out of the job, lists nothing, and no field of it is read; a link to another folder of the job, or into a OneDrive library, is listed. A file for all jobs must lie, by its real path, inside `<userData>/work-templates/shared`. A remote key's list leaves out a job's template whose real file it could not name itself, and its make, rename, move, remove and field read are held to the same (`reachesFile`).

**A Word template he edited.** The document kind edits a `.tcdoc` made of a Word file, written beside it under the same name, never the file. So `Templates/Game report.tcdoc` beside `Templates/Game report.docx` (job's or all jobs') is one entry, the `.tcdoc`, which holds his edits; its `twin` is the Word file. What makes them one is kept in `work_templates_pairs (doc, word, paired)`: the document by its real path (`docKey`), the Word file by its identity (`fileIdentity`: disk, inode and birth time, so a number the disk gives again later is another file). The document kind saves a `.tcdoc` by writing a new file and renaming it over the old, so a document's identity changes at every save; its path changes only by this pillar's rename and move, which record the pair again. No editor writes the Word file, and a rename or a move by link keeps its identity; a move records the identity it published there, never what the new name holds when read again. What is known there wins. Two files never seen before are paired once on proof that the document was made of that file (`madeOf`): the import writes `source { name, format, importedAt }` into the `.tcdoc`'s `sidecar.json`, and it must name that Word file by its file name, as Word, imported no earlier than the Word file was last written (2 s of slack for a coarse disk clock); the pair is then kept. His own document "Letter" beside an unrelated `Letter.docx`, a document read from another Word file, or a Word file written again after the import, are two tiles, each changed alone. After this pillar renames or moves a pair, the pair is kept under the new files' identities (a move by copy gives new ones), so the import's record, which still names the old file, is never asked again; a pair renamed to Match report, or moved to "Game report 2", stays one. After it renames or moves a lone document or Word file beside a file of the other kind and its name, the two are kept apart, so the import's record, which names files by name alone, never joins two files this pillar put side by side. What stays open: two files put side by side by hand or through Files, never seen before, are still judged by the import's record. Its fields are read from the `.tcdoc`'s markdown preview. A rename and a move of a pair take both files: a rename refuses a name either file could not take, a move gives both one free name. A remove takes only the file he pressed on, to Trash or deleted: the import's record of a name and a time can join a document to an unrelated, older Word file of that name, nothing yet proves a pair beyond it, so the Word file stays and shows as its own tile. Deleting it is his own second press.

`registerStarterTemplates(kind, entries)` puts an editor's own starter files in the All jobs group. It is the file's own state, so a pillar may call it when it loads, before or after this module starts. One with the name of one of ours takes ours' place and its key, and is shown once.

## Fields (`src/shared/work/templates.ts`)

A field is `{{Client}}` typed in the file's text: two braces, a name of 1 to 40 letters, digits and spaces, two braces. Names match without case, and outer spaces do not count (`fieldKey`).

| Field | Filled with | Asked |
|---|---|---|
| `{{Date}}` | the caller's day in the long form ("November 23, 2026"); in a sheet, a cell that holds only `{{Date}}` and wears a date format becomes a true date and keeps that format | never |
| `{{Name}}` | the setting `work.ownerName` | never |
| `{{Job}}` | the workspace's name | never |
| any other name | what he types, or what a caller passes | in the dialog, in the file's order, each name once |

- The window sends its own day (`today: YYYY-MM-DD`). A tool, and a caller that sends none, gets the host's own day. A caller may pass `Date`, `Name` or `Job` in `fields`; its value wins, and a `Date` given in words is written as words in a date cell too.
- A field with no value stays in the file as written (`LEAVE_UNFILLED`; flip it and the field is taken out). `{{Name}}` stays when LifeOS has not given the host his name.
- A lone `{{Date}}` cell in a format that shows no date gets the day in words: a bare number would say 46349.
- `Template.fields` holds only the fields the dialog asks for.

## The fill (`ooxml.ts`, `zip.ts`, `deckFill.ts`)

The fill always runs on a scratch copy.

| Form | Parts read | A paragraph is | Text is | Filled by |
|---|---|---|---|---|
| docx | `word/document.xml`, headers, footers, footnotes, endnotes | `w:p` | `w:t` | `fillOffice` |
| xlsx | `xl/sharedStrings.xml`, inline strings in `xl/worksheets/*.xml`, the page header and footer | `si` or `is` | `t` | `fillOffice` |
| pptx | `ppt/slides/*.xml`, in the deck's order | `a:p` | `a:t` | the slides pillar (`fillDeck`); `scanOffice` only reads a deck |

- Word and PowerPoint split a typed `{{Client}}` over runs. The scan joins the text runs of a paragraph and finds fields in the joined text. A run belongs to the innermost paragraph around it, so a text box inside a paragraph is its own. A tab or a line break (`w:tab`, `w:br`, `w:cr`; a deck's `a:br`) ends the stretch that is joined: he sees a gap there, so `{{Cli`, a tab, `ent}}` is no field, for the scan and the fill alike.
- A brace written as a character reference (`&#123;`, `&#x7B;`) is a brace: the fill reads the same decoded text the scan does.
- The Word and Excel fill writes a value into the run where its field starts and empties the rest of that field's runs. Every run stays, with its formatting. A filled run that starts or ends with a space gets `xml:space="preserve"`.
- XML is read by pattern under one rule: an opening tag may carry attributes and spaces, a closing tag may end in spaces (`</a:t >`), and an attribute is read in either quote with spaces around its `=` (`attr`, ooxml.ts). The prefixes are the ones Office and python-pptx write (`w:`, `a:`, `p:`, none in a sheet); a part written with others reads as holding no field and is left as it is.
- XML is edited as text between known tags. Values are escaped, and characters XML cannot hold are dropped. In a sheet's page header an ampersand in a value is doubled, since Excel reads `&` there as a code.
- Only the parts that held a field with a value are written again. `zip.ts` copies every other part with its compressed bytes as they were, in the same order. It uses `node:zlib`; the app declares no zip library of its own.
- The fill never joins across a paragraph. A field it cannot join is left as written and named in `unfilled`. Cases seen: a field broken over two table cells, and over two paragraphs.
- A sheet's fields are listed in the cells' order, sheet by sheet, not in the shared strings' order.
- A deck: `fillDeck` reads it through `ctx.convert({ from: 'pptx', to: 'deckinfo' })`, which names slides and shapes as `slides_read` does, then sends one `runs` op for each shape that holds a field through `pptxedit`, not strict. The op names every paragraph and run of the shape by where it was read (`from`), so each keeps its own look and its link (a hyperlink lives in the run's properties), and only the runs a field lay in change their words, as Word's fill does (`fillRuns`); no field is filled across a line break. A table's cell takes the same op by its row and column, with its runs read from the slide's own XML (`deckCellRuns`, by the slide and shape ids the read gives), since the read gives a cell's text alone; a cell whose runs cannot be read, or whose runs do not account for every character of the text the read gave (`accounts`), is left, its fields named, since the plain `cell` edit gives each paragraph its first run's look and drops a link. Each edit is held to the slides pillar's own schema (`SlideOpSchema`) before it is sent: one the edit would refuse (a value that makes a run longer than 20,000 characters) is left, so the rest of the batch still goes in. A shape read at the read's cap of 400 runs, or with a run cut at its text cap, is left and its fields named in `unfilled`. A shape read without its runs takes a `text` op, which gives a filled paragraph its first run's look. Speaker notes are not scanned. No code of this pillar writes a `.pptx`.
- A deck's scratch copy says nothing of where its deck came from, so the fill says it: every job it hands the runner (the read and each batch of edits) carries `shared: true` when the template's file is one others can open (`sharedOf` of its source), and such a job never leaves this host (formats/jobs.ts `sharedJob`).
- A filled Word or Excel file is written whole beside the scratch copy and only then takes its place; a filled deck is the slides pillar's second file, renamed over the copy. A write cut short (a full disk) leaves the copy as it was, so a make never places a file cut short: it places the plain copy and names its fields in `unfilled`, and the host's log says why.
- When no host can run the deck edit (no python-pptx in reach), the deck is placed as a plain copy and every field is named in `unfilled`; the host's log says why.

### Our own kinds

| Saved as a template from | Kept on the shelf as | Why |
|---|---|---|
| `.docx`, `.xlsx`, `.pptx` | a copy, as it is | nothing is lost |
| `.tcdoc` with no field (the markdown preview inside the file is scanned) | a copy, as it is | nothing is lost |
| `.tcdoc` with any field, Date, Name and Job among them | `.docx`, through `work.formats.export` | one fill, in one place |
| a `.tcdoc` already on the shelf (the document kind's twin of a Word template he edited, or one put there by hand) | as it is; a make with a field in it exports it to Word first and fills that | the made file is Word, as every made document is |
| `.tcsheet` that is open in a canvas item and is his own | `.xlsx`, through `work.sheets.export` | Excel is where sheets are going |
| any other `.tcsheet` | a copy, as it is | its export is by item |

`work.sheets.export` writes its file among the item's own files, where the sheets pillar keeps its exports; the save copies it from there and leaves it as that pillar left it. It is never asked for a sheet others can open. `work.templates.fields` answers `later` for such a sheet: what it asks for is read from the Excel file the save makes, so the window says it after the save. A `.tcsheet` he moves into `Templates` by hand is listed and used as a plain copy with no fields, and its state is not opened. A `.tcdoc` there asks the fields its preview holds; a make turns one with any field into Word through `work.formats.export` and fills that (asked as the host's own read, `SHELF_READ`, of the one entry the make already admitted for its caller: a key's export would be refused a file in the host's own data, though the key may make from it), and where the export does not answer it is placed as a plain copy with every field named in `unfilled`. The `.tcdoc` to `.docx` path loses what the exporter loses today.

## Making a file (`make.ts`, `place.ts`)

One path for the shelf, Files' New, the tools and the other pillars:

1. Resolve the template.
2. Copy its file to `<userData>/work-templates/scratch/<random>/` and fill it there. The file is read by its real path, resolved in the same step as the shelf's checks of it (`real`), so a link moved while the make runs cannot hand it another file; a save reads its source the same way.
3. `lookOf(ctx, workspaceId)` (below). It answers null today.
4. Name it: the caller's `title`, else the template's name, then " - " and the first asked field that has a value ("Game report - Central at North"). `fileStem` drops what a disk refuses.
5. Place it. His own press (a window, a paired device) asks Files first: `work.files.make { workspaceId, at: into ?? the workspace's folder, kind, name, from: scratch, op }`. Files then picks the name and the place's form and asks what it must in a shared place. Files is asked only once the workspace folder's place lists the verb (`FilePlace.can` in `work.files.places`, read by `folderCan`): until Files builds its changes that list is empty and its door refuses the verb in its own words, which is no refusal of his. While the folder cannot make, and always for a thread's, another pillar's or another host's call, the file is copied into the workspace's own folder under a free name, never over another file. That copy passes Files' door first (`admitDirect` in place.ts): `sharedOf` says by the folder's real path whether others can open it (a workspace kept in OneDrive, a `Templates` folder linked into a library), and `admitWrite` says who may change it there. A thread's or another pillar's file is refused there in one sentence (a held act is Files' alone to make); a key needs `approve`; his window's press is the question asked. Save, rename, move and the delete with no Trash pass the same door. `into` is then taken only when it is a folder inside the workspace's own folder, made if missing; anywhere else is refused in one sentence.
6. Answer `{ source, kind, title, unfilled }`. The scratch folder is removed, also on a failure.

Opening is the caller's: the window opens the file in a Files tab; a tool calls `ctx.canvas.open`.

`ctx.peer` refuses its own host, so Files' `work.files.make` and `work.files.trash`, and the exports of formats and sheets, are called through the module's `handle` from the registry (`WORK_MODULES`), with the real caller, so Files' door judges who pressed.

A remote key makes, saves and lists only for a workspace whose folder it may reach (`ctx.reaches`). A save's source must be in its reach too, but for a starter or a template for all jobs on that workspace's shelf: those lie in the app's own folders, which no key's fence names, and "Edit a copy" copies one.

## The wire (`src/shared/contract-work-templates.ts`)

| Method | Cap | Answers |
|---|---|---|
| `work.templates.list { workspaceId }` | read | `{ templates, hidden }` |
| `work.templates.make { workspaceId, template, into?, fields?, today?, title? }` | operate | `{ source, kind, title, unfilled }` |
| `work.templates.save { workspaceId, source, name?, everywhere? }` | operate | `Template` |
| `work.templates.rename { workspaceId, template, name }` | operate | `Template` |
| `work.templates.move { workspaceId, template, everywhere }` | operate | `Template` |
| `work.templates.remove { workspaceId, template, confirmed?, version? }` | operate | `{ trashed?, confirm?, version? }` |
| `work.templates.unhide { workspaceId, template? }` | operate | `{}`; with `template`, that starter alone (the undo of one Hide) |
| `work.templates.fields { workspaceId, source }` | read | `{ fields }`: what a file would ask for as a template, read where it lies |

- The push `work.templates { workspaceId | null }` follows every change; null means every workspace's shelf (a template for all jobs was saved, moved or removed).
- Every method is carried to the workspace's host, so a Mac window reaches a shelf on the box. The phone has no rows.
- **Remove.** A starter is hidden in that workspace. One of the job's own goes to Files' Trash where the folder's place lists `trash`, and the answer's `trashed` holds the rows Put back takes. Where Files has none yet, and for a template for all jobs (it lies in the app's own data), the first call answers `{ confirm: true, version }` and deletes nothing; the window asks him and calls again with `confirmed: true` and that `version`, which names the file as it was then (its disk, inode, size and time). A file that is not that one any more (renamed away, another saved under its name) is left, and the call is refused: "That template changed while it was asked about: nothing was deleted." A yes with no version deletes nothing, and another host of his cannot give one. A key's Hide is held to its reach of the workspace, as every other change is.
- **Rename and move** act on the files as they were checked: each by its folder's real path, resolved once, and only while it is still the file the shelf's read saw (by inode). Each file moves with a link and then the old name; across disks, or on a disk with no hard links, it is copied to a hidden name of the new folder, which nothing else names, and that name is linked to the new one, so what was published is known without looking at the new name again; neither ever replaces a file. The old name is removed only once it is claimed: renamed in one step to a hidden name in its folder, then seen to hold the file that was moved. A file an editor saved there before the claim is given its name back, the move is taken back and refused ("That template changed while it moved: it was left where it was."); one saved after the claim simply lands under the old name, which nothing removes. Taking a move back removes the new name only while it still holds what the move published (by inode, size and time: a freed inode's number is soon reused), so a file another window saved there, before or after the move looked, stays; when the old name cannot be taken at all (a file held open), the new name is taken back and the error is said. A change of two files that fails at the second takes the first back the same way, bound to what it published. On a disk with no hard links at all (a share, some FAT volumes) the new name is an exclusive copy with no link to bind it to what was written, so nothing proves what it holds by the time the move is taken back: it is never removed then, the old name keeps its file, and the move fails saying where a copy may be left ("A copy may be left at Letter.docx."). A delete with no Trash claims its file the same way and checks each against the version he was asked about before any goes; a claim or a removal that fails gives back every file not yet gone, so no file of his is left under a hidden name; a file given its name back never lands over one that took the name meanwhile (it takes the next free name). A change of case alone is one rename only when the disk reads both names as the same file. The answer names the file as written: `LETTER.DOCX` renamed to Memo is `Memo.DOCX`.
- **A link** on the job's shelf (to another file of the job, say `../Forms/Letter.docx`) is renamed in its folder, where it leads where it led, but never moved to another folder, where a relative link would lead elsewhere or nowhere: "That template is a link to a file elsewhere: move the file it links to instead."
- **The key's fence** comes before the shelf is read, for every method: a key outside a workspace learns no template's name, not even that one is missing. A save or a move into the job's Templates folder is held to where that folder really is, resolved once (`resolveDir`): every check is made on that folder, the file is written there by its real path, and a save whose folder name leads elsewhere by the time the export is done writes nothing ("That Templates folder now leads somewhere else: nothing was saved."). It is held: a key must reach it there (`reachesDir`), and the shelf must read it there (`jobShelfReads`, Files' `locate`), or nothing is written ("This job's Templates folder leads out of the job, so the shelf would not show a file put there."). Each file a rename, move or remove changes, the Word file of a pair too, must be in the key's reach. The host's own folder for all jobs stays the one exception: no key's fence names it, and a key that reaches the workspace may copy, move and make from what is there.
- **A name** goes through `fileStem`, which also drops a start the shelf never shows (a dot, or Office's `~$`), so a rename or a save never strands a template under a name the shelf hides.
- **Save** copies. The source is never moved, renamed or written, whoever can open it. It takes a file on this host (`{ at: 'file' }`, or an Office item's `{ kind: 'path' }`).

## Tools (`tools.ts`)

Listed for a workspace's threads; a Work Chat has no shelf and gets none.

- `template_list` (read only): each template's name, kind, group and fields.
- `template_make { template, fields?, title? }`: makes the file in the workspace's own folder, opens it in the thread's canvas, answers the item id and the fields still unfilled. It takes no folder. Where others can open the workspace's folder (it is kept in OneDrive, say) the make is refused in words, as `template_save` is for a `Templates` folder others can open: neither tool writes a file there.
- `template_save { item, name?, everywhere? }`: puts the file of one of the thread's own canvas items on the shelf.

A play is text, so "start the game report" is a step that says so; the play's thread calls `template_make`.

## The screens (`src/renderer/src/work/templates/`)

Every part is a Kobra part (`components/README.md`). One tile, one grid and one dialog serve the shelf, New and the fields.

- **The tile** (`Shelf.tsx`). The shared `Button` laid over the whole tile (`ROW_OPEN`): the plate, then one 13/20 line with the kind's glyph 8px from the name, cut to one line; while the name is cut, its whole is the press's tip (`useTruncated`, the measure `TruncateTip` uses). 6px of padding against a -6px margin so tiles align to the grid's edge, a 12px radius, the focus ring inside. It presses as a row whose open control is laid over it (`ROW_HOLDS`, keyed to the press): a 5% wash on hover, 12% at once while pressed, nothing scaling (DESIGN.md's motion table: a row's press steps its fill and never scales; the plan's `scale(0.97)` gave way to it). While its menu is open the tile keeps the 5% wash, as a rail row does. The press's label is the name and its description the kind ("Document", "Sheet", "Deck"), for someone who cannot see the glyph or its tint. No badge, no description, no count. Starters and his own look the same; only their menus differ. The glyph turns to a `Spinner` when a make, or an Edit, runs past 150 ms (`SPIN_AFTER_MS`); the tile does not move.
- **The plate** (`Plate`) is a small drawing of the kind in the tile's own measure, until Files' thumbnails land and take its place: a document is a heading and lines of writing, a sheet a grid with a head row, a deck a title slide. It shows no glyph, so the glyph stands once, on the name's line. The glyph on the name's line wears its kind's tint (`kind-doc`, `kind-sheet`, `kind-slides`; DESIGN.md "File kind tints"): a template's tile is a file's tile.
- **The groups** (`model.ts` `shelfGroups`): the workspace's name (his own, then the sector's starters, each by name), then "All jobs". A group with nothing is not drawn. Each is a 12px muted label over a grid: `repeat(auto-fill, minmax(148px, 1fr))` on the page, three columns in the dialog (two under 640px), gap 16px by 12px.
- **Keys**: Tab stops twice on the shelf, at the current tile and at its ⋯. Arrows walk the tiles across both groups, Home and End jump to the ends, Return makes. In the dialog the first tile takes the focus when the shelf arrives, unless he has moved it.
- **The Templates view** (`view.ts`, `TemplatesView.tsx`; id `templates`, order 3.6, `readsLifeos: false`, chunk `work-templates-view`). The header carries a ghost "Add…" (the system's file chooser), always its last control, and before it, only when starters are hidden over a shelf with tiles, a ⋯ with "Show hidden"; Add… never moves for it. The shelf is read as DESIGN.md says a page reads a host (`useHostRead` in `data.ts`, the view and the dialog alike): it waits for the socket, asks again on every new socket until it has answered, and a refresh that fails (a push's re-read) keeps the shelf on screen. It asks again on a `work.templates` push and on a `work.files` push whose folder is the job's Templates folder (`namesTemplatesFolder`), so a file put in or taken out through Files, Trash's Undo among them, shows on the shelf. Loading is skeleton tiles in the loaded tile's shape (the plate, then a 14px square 8px from the name's bar); an error is the view's state line (`ViewStateLine`: the word, the host's detail, Retry), its detail's whole text a tip while the line cuts it, and Add… is off while the shelf has failed (it stays on while the shelf loads: a save does not need the shelf). An empty shelf is "No templates": when he hid the starters its line says how many and its action is "Show hidden" (DESIGN.md "Loading and empty states"), else it has none, since Add… is the header's. A file dropped on the view becomes a template: the view takes the drop as an inner surface, so no thread starts. One add runs at a time for a workspace, from Add… or a drop; while one runs, a drop is refused where he can see it (no wash, no copy cursor). Each file is tried, and one message names the files left out and why. Add and a drop take a file of the workspace's own host. Twenty-three files, checked in under `resources/work-templates/<sector>/<Name>.<form>` and packed with the app (both builder configs hold only negative globs, and none matches the folder). `starters/manifest.ts` lists them: sector, name, kind, form and the fields each asks for.

|---|---|

| Hypixel | Shot list (sheet; Video) · Video brief (document; Video) · Script (document; Video) · Review deck (deck; Video) |
| Purdue | Memo (document; To, Subject) · Event run of show (document; Event) · Travel budget (sheet; Trip) · Program update (deck; Term) |

**To make more, or change one.** Add its row to `manifest.ts`, write its fixture (`starters/docs.ts`, `sheets.ts` or `decks.ts`), then run the build by hand and check in what it wrote:

```
bun --preload ./scripts/lib/electron-stub.ts scripts/build-work-templates.ts
```

The build is never run at build time. It removes any file the manifest does not name. Documents and sheets come out the same bytes each run; a deck does not, since pptxgenjs stamps the time.

- **Documents** are block fixtures written through work-kit's `writeDocx`, then `themeDocx` (`starters/docx.ts`). The pass is needed because `writeDocx` writes the `docx` library's default styles, which hold hex colours. It writes Word's built-in styles on theme colours and theme fonts, sets 11 pt body and US Letter with inch margins, gives table rules a theme tint, gives an empty cell's paragraph no space after it as every cell's, hangs a check item's box, drops the writer's `<w:tblHeader w:val="off"/>` from rows that are no head (work-kit's `readDocx` counts the tag without reading its value, so every row would read back as a head), and fixes the core dates. Then `keepTogether` keeps short things whole on paper: a list keeps with itself, a table moves whole (no row splits, every row but the last keeps with the next), and a line that leads into a list or a table keeps with it, as a heading does by its style. `headerFromPageTwo` gives the document a first page of its own (`w:titlePg`, and no header or footer named for it), so the header and the page's number print from page two on as the sheets' header does, and a one-page document has neither. No first-page header part is written: the app's reader keeps the setting but counts a first page's own header as lost, and a made document would open with a line saying so. A page break before a heading becomes the heading's own `pageBreakBefore`. It shrinks to the dates and the keeping once `writeDocx` writes its own styles and theme (DOC3, DOC5).
- **Sheets** are written by `starters/xlsx.ts`: one fixed style sheet with Excel's named styles (Normal, Heading 1, Heading 2, Total, Input, Note, Currency, Percent), date and number formats, widths, formulas each written with its result on the sample rows (the fixture works them out from its own numbers, so a CSV export, a preview or the phone shows the totals; Excel works them out again on open), a frozen head, pick lists on the rows they serve, and print set-up. The page header prints from page two on (`differentFirst`): page one's title says it already. A count of done rows counts only rows that hold a task (`COUNTIFS` with the task's column not empty), and a total or a difference of actuals counts the entries (`COUNT`), so an entered zero shows and a blank shows nothing; a total difference sums the differences of the rows that have an actual, and a balance waits for both sides. An Invoice line's amount waits for both its quantity and its rate. It is not a second sheet writer: it knows only what the starters use and imports nothing of the sheets pillar.
- **Decks** are inputs to the slides pillar's own `slides_new`, run by the build from the slides module's tool list. No code of this pillar writes a `.pptx`. A deck keeps `slides_new`'s look.

The rules every starter keeps, each held by `starters.test.ts` over the checked-in files:

- In documents and sheets, colours are theme slots with tints and automatic ink, and fonts are the theme's heading and body: no literal colour outside `theme1.xml`. So a job's look recolours all of it by swapping one part.
- No picture, logo or embedded font. One thing is let through by name: a deck's chart keeps its numbers in `ppt/embeddings/Microsoft_Excel_Worksheet.xlsx`, as pptxgenjs writes it.
- No name of an employer, school, league, game or person (a deny list, whole words, every part). Where one belongs the file says `{{Job}}`, `{{Name}}` or a named field. Sample rows are plainly made up ("Item one").
- Every field in a starter's manifest row is in its file, in that order, and no other.
- On paper: no cell paragraph has space after it, and no list or table is split or cut from the line that leads into it. In sheets: the header from page two on, no formula that reads a zero as nothing entered, done-counts and pick lists on task rows only, and the Invoice's due date driven by its one terms cell.
- Each document reads back through work-kit's `readDocx` with the fixture's headings, each sheet through `importXlsx` with its sheet names, and each document and sheet fills with nothing left.

`starters/shelf.test.ts` holds the shelf to the manifest: each sector's workspace lists its starters and every job's, and each is found by its key.

LibreOffice draws a Word run or fill that is `auto` with a theme colour in automatic ink, so there a document's headings, rules and table heads are black with no fill; Word shows the theme's colours. Sheets show their theme colours in both.

## A job's look (`look.ts`)

`lookOf(ctx, workspaceId): JobLook | null`, with `JobLook = { theme: OfficeTheme; logo? }`. It answers null. `make.ts` asks it once, after the fill and before the file is placed. The feature that gives a job its colours, fonts and logo fills `lookOf` and writes the one swap of `theme/theme1.xml` in the scratch file. `OfficeTheme` is work-kit's (`work-kit/format/theme`).
